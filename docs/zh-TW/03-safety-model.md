# 3. 安全模型

安全模型保護檔案意義、存取邊界與可回復性。它是框架契約的一部分，不是選配偏好。

## 安全不變量

### Scope boundary

只能檢查與變更使用者指定的 target。除非模式與核准允許，不可沿著連結進入其他工作區，也不可遞迴進入子樹。

### Secret black box

將憑證儲存、私人設定、金鑰材料、工作階段檔案，以及被標記為敏感的檔案視為不透明。盡量只使用 metadata、檔名或已核准的清冊訊號。不可複製、印出、索引、摘要或在報告中包含其內容。

### Path dependency gate

移動或改名前檢查可能失效的參照：相對連結、腳本、import、manifest、捷徑、自動化輸入與文件化路徑。如果無法安全檢查，就維持不動並回報不確定性。

### Canonical-source protection

不可因另一份檔案看起來較新、較乾淨或較完整就取代或刪除來源。要從明確 metadata、所有權、參照、版本歷史或使用者確認建立權威性。

### Destructive-action gate

刪除需要明確確認。「刪除重複檔」不足以授權不可逆動作，尤其 identity、保留政策或參照仍不確定時。優先使用可回復封存，或只回報候選項目。

## 核准層級

| 動作 | 預設 | 核准 |
| --- | --- | --- |
| 讀取範圍內允許的 metadata 與內容 | 允許 | 不需額外核准。 |
| 產出 inventory 或 dry run | 允許 | 不涉及變更核准。 |
| 建立報告或 change ledger | 可在選定位置建立 | 不涉及變更核准。 |
| 移動或改名 | 不自動執行 | 明確核准 change set。 |
| 封存 | 不自動執行 | 明確核准，除非既有政策明確授權。 |
| 刪除或覆寫 | 預設阻擋 | 逐項明確確認。 |

## Scan 失敗時

Scan 失敗不是猜測的許可。停在最小安全邊界，回報已檢查內容、缺少的證據與原因，未驗證項目維持不動。

## 驗證與掃描分開

Preflight scan 通過，只代表 Agent 能在宣告規則內檢查 target，不代表整理正確。成功的 organization 需要：

1. 已核准動作；
2. 實際變更證據；
3. post-condition 檢查；
4. 範圍外變更檢查；
5. 清楚列出 unresolved items。

## 以回復為導向

用能達成目標的最小破壞性操作。Ledger 保留原始名稱，批次小到可審查，遇到意外衝突就停止。如果提供者不能保證安全回復，不要暗示可以 rollback。
